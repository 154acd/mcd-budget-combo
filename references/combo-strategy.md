# 搭配策略与输出模板（mcd-budget-combo 专用）

> 本文件规定「如何从菜单枚举候选搭配」与「如何输出报告」。SKILL.md 只规定输出必须包含的要素；分类关键词、枚举规则、报告模板原文以本文件为准。

## 1. 菜单解析与分类

### 1.1 输入格式（combo_planner.py 的契约）

`plan` 子命令接收 query-meals 返回的 `data` 对象（JSON 文件）：

```json
{
  "categories": [{"name": "随心配\n1+1", "meals": [{"code": "9900013304", "tags": ["超值百种组合随心配"]}]}],
  "meals": {
    "9900013304": {"name": "人气经典随心配", "currentPrice": "14.9", "originalPrice": "14.9", "canWithOrder": false}
  }
}
```

> planner 只读取上述结构中的 `categories[].meals[].code/tags` 与 `meals{}` 的 `name/currentPrice/canWithOrder/discountType` 字段；其余字段（image、withOrder、originalPrice 等）可裁剪以减小文件体积，裁剪不影响结果。

### 1.2 分类规则（按名称关键词，优先级从高到低）

| 类别 | 判定规则（名称包含任一关键词） | 件数 | 主食数 |
|---|---|---|---|
| 周边（**剔除**） | 帽、毛绒、周边、挠、捶背、徽章、玩具、摆件 | 0 | 0 |
| 酱料（**剔除**） | 名称以「酱」结尾且价格 < 5 元 | 0 | 0 |
| 随心配 | 随心配 | 2 | 1 |
| 多人/亲子餐 | 双人餐、亲子餐、分享餐 | 4 | 2 |
| 套餐 | 套餐、三件套、四件套、单人餐、开心乐园餐 | 名称含「三件套」→3；「四件套」→4；「开心乐园餐」→2；其余→3 | 1 |
| 小食拼盘 | 小食拼盘、随心拼、四宫格、双拼 | 名称含「N件」按 N；否则 4 | 0 |
| 主食（单品） | 堡、卷（且不属于上述类别） | 1 | 1 |
| 小食 | 薯条、薯饼、薯、鸡块、鸡翅、鸡排、翅、派、玉米、苹果片、芝士条、扭扭薯、心形薯饼、脆汁鸡、蘸酱炸鸡 | 1 | 0 |
| 甜品 | 冰淇淋、圆筒、新地、麦旋风、雪冰 | 1 | 0 |
| 饮料 | 可乐、雪碧、咖啡、美式、拿铁、奶铁、红茶、绿茶、奶、汁、柠、橙、燕麦、可可、卡布奇诺、阿芙佳朵 | 1 | 0 |

> 通用兜底：名称含「N件」字样时件数取 N；无法归类 → 其他（件 1、主食 0）。

### 1.3 预过滤（枚举前必须执行）

1. **随单购商品排除**：`discountType="随单购麦金卡优惠"` 或 `canWithOrder=true` 的商品——现价需随单购麦金卡才享受，不买卡即原价。默认排除；如用户明确持有麦金卡，可在方案中单独成类并标注「需随单购麦金卡」。
2. **周边/酱料剔除**：见 1.2，不作为「吃饱」候选。
3. **超预算单品排除**：单价 > 预算（外送场景：> 预算 − 配送费 − 打包费）的商品不进入候选池。
4. 按 `code` 去重（同一餐品可能出现在多个分类）。

## 2. 饱腹度三维度

| 维度 | 计算 | 展示 |
|---|---|---|
| 件数 | 按 1.2 件数表求和 | 「约 N 件」 |
| 主食数 | 按 1.2 主食数求和 | 「含 N 份主食」 |
| 千卡参考 | 传入 nutrition.json（list-nutrition-foods 的名称→能量表）后按名称匹配求和；匹配不上的不计入 | 「约 NNN 千卡（M/M 项有数据）」；无 nutrition.json 时**不展示千卡，不得编造** |

> 套餐/随心配的内部构成需 query-meal-detail 才能展开；未展开时千卡按「暂缺」处理，只累计能按名称直接匹配的单品。

## 3. 四种枚举模板（combo_planner.py 的算法）

候选池经过 1.3 预过滤后（通常 < 30 件），按以下四模板各生成候选，同店合计保留 ≤ 6 个进入 calculate-price 核价：

### 3.1 max_satiety — 最饱腹

1. 锚点：在「主食数 ≥ 1 且目录价 ≤ 预算」的餐品中，按（主食数降序 → 件数降序 → 价格升序）取第 1 名；
2. 补件：剩余额度内，按「件数/元」性价比降序添加不重复的小食/饮料/甜品，每加一件保持总价 ≤ 预算；
3. 剩余额度 < 池中最低单价时停止。

### 3.2 max_pieces — 件数最多

1. 全池按（件数降序 → 单价升序）排序；
2. 贪心循环：每次取当前「件数/元」性价比最高的项 +1 件（允许同一项买 2 件，如随心配 ×2），保持总价 ≤ 预算；
3. 无法再添加时停止。

### 3.3 classic — 经典省心

1. 在带「经典精选 / 爆款 / 人气 / 人气经典」标签、或分类为「精选单人餐 / 大堡口福」的套餐/随心配中，选目录价 ≤ 预算者；
2. 按（件数降序 → 价格升序）取第 1 名，单套输出，不做添加。

### 3.4 coupon_driven — 用券多吃

1. 遍历 coupons.json 中每张券（来自 query-store-coupons，字段 title / couponId / couponCode / products[]）；
2. 仅当券的全部 `products[].productCode` 都在菜单中、且这些商品的目录价合计 ≤ 预算时才可用；
3. 组合 = 券商品 + 用剩余额度按「件数/元」补不重复小食/饮料；
4. 无可用券时本模板不产出。

### 3.5 去重与排序

四模板结果按 items 的 (code, quantity) 集合去重；最终按（主食数降序 → 件数降序 → 目录价升序）排序输出。

## 4. 输出报告模板（每家门店一块，原样套用）

```markdown
【门店 {n}】{storeName} · {distance}m · {营业状态：营业中/休息中} · {当前时段判断，如「当前为夜市时段」}
可用优惠券（query-store-coupons 实时查询）：
- {couponTitle}（{tradeDateTime}，适用：{productNames}）{状态：可用 / 当前不在门店菜单，暂不可用}

搭配方案（预算 {budget} 元；价格均为 calculate-price 实时核价）：
A. 最饱腹｜{itemsSummary} —— 约 {pieces} 件、含 {mains} 份主食，核价 {price} 元，余 {remain} 元
B. 件数最多｜{itemsSummary} —— 约 {pieces} 件，核价 {price} 元，余 {remain} 元
C. 经典省心｜{itemsSummary} —— 约 {pieces} 件，核价 {price} 元，余 {remain} 元
D. 用券多吃｜{itemsSummary}（用券：{couponTitle}）—— 核价 {price} 元，余 {remain} 元

提示：回复「领券」可查看并领取优惠券；确定方案后可说「就点 A 方案」（下单前会复述订单与金额，经你确认后才提交）。
```

D 方案（用券多吃）无产出时，固定写为：`D. 用券多吃｜无（本店可用券的适用商品均不在菜单 / 暂无可用券）`。

A/B/C 方案无产出时的固定文案：

- A 无产出：`A. 最饱腹｜无（{budget} 元内没有含主食的套餐可选；最便宜主食单品「{name}」目录价 {price} 元，还差 {gap} 元）`
- B 无产出：`B. 件数最多｜无（{budget} 元内无满足条件的餐品组合）`
- C 无产出：`C. 经典省心｜无（{budget} 元内无经典套餐可选）`

任何策略行都不得省略、不得用其他策略的方案充数；若四行全部无产出（预算极低），保留差额建议并说明「该预算内可选餐品非常有限」。

**输出硬性要求**：
1. 每个价格后必须标注数据来源为 calculate-price 实时核价，不得直接使用菜单目录价充当最终价；
2. 券必须标明「可用 / 暂不可用（适用商品不在售）」；
3. 外送场景：配送费 + 打包费单独列示一行，并从预算中扣除后再出方案；
4. 无千卡数据时不出现千卡字段；有数据时标注「约 NNN 千卡（M/M 项有数据）」；
5. 结尾必须给出「领券 / 就点 X 方案」的引导语。

## 5. 边界情况速查

| 情况 | 处理 |
|---|---|
| 预算 < 门店最低在售价 | 不输出搭配；告知最低价商品与差额，给「加 X 元可得 XX」建议 |
| 门店无可用券 | 输出无券基线方案；提示 available-coupons 有可领之券，询问是否「领券」 |
| 券适用商品不在菜单 | 券行内标注「当前不在门店菜单，暂不可用」，不计入方案 |
| calculate-price 核价 > 预算 | 丢弃该候选，取同策略下一候选；全部超预算则输出最接近方案并说明差额 |
| 外送配送费 + 打包费 > 预算 × 30% | 报告中显著提示「外送费占比过高，建议到店自取」，并附到店方案对比 |
| 随单购商品 | 默认排除；用户明确持麦金卡时单独成类并标注 |
| 周边/酱料 | 不进候选池 |
| 菜单为空或查询失败 | 如实告知该店菜单暂未获取到，跳过该店，不编造 |

## 6. combo_planner.py 命令契约

```bash
# 生成候选搭配（零网络、零 Token 的本地计算）
python scripts/combo_planner.py plan \
  --menu menu.json \                 # query-meals 的 data 对象
  --budget 30 \                      # 预算（元），外送场景传扣除配送费后的值
  --coupons coupons.json \           # 可选：query-store-coupons 返回的券数组
  --nutrition nutrition.json \       # 可选：list-nutrition-foods 的 {名称: 千卡} 映射
  --max-candidates 6                 # 可选：进入核价的候选上限，默认 6

# 自检（内置断言，无需任何输入文件）
python scripts/combo_planner.py selftest
```

> Windows 环境下，--menu / --coupons / --nutrition 一律传 Windows 绝对路径（如 `D:\work\menu.json`），不要用 /tmp 等 Unix 路径；运行脚本使用本机 Python 可执行文件的绝对路径。

`plan` 输出 JSON 结构：

```json
{
  "budget": 30.0,
  "candidates": [
    {
      "strategy": "max_pieces",
      "items": [{"code": "9900013304", "name": "人气经典随心配", "price": 14.9, "quantity": 2}],
      "catalog_total": 29.8,
      "pieces": 4,
      "mains": 2,
      "kcal": null,
      "kcal_note": "无营养数据",
      "coupon": null
    }
  ]
}
```

> 注意：planner 只做「目录价层面的候选筛选」，**最终价格一律以 agent 调用 calculate-price 的返回为准**；planner 输出的 `catalog_total` 超预算的候选应在核价前丢弃。
